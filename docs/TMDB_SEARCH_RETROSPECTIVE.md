# TMDB 检索链路复盘备忘

日期：2026-06-28

## 背景

SaikoSubStudio 的 TMDB 关联逻辑经历过多次小步迭代，目标一直在变化：

1. 从脏字幕文件名中提取可检索片名。
2. 支持中文、英文、剧集季集号、发行版本参数。
3. 防止弱文件名如 `2024.1080p.HEVC.AC3.5.1.ass` 被误当片名。
4. 防止二次检索失败覆盖已有正确片源信息。
5. 在候选结果中选择最可靠的 TMDB 条目。

这些目标彼此有张力：越积极回退越容易命中，也越容易误命中；越保守越安全，也越可能让用户手动补充。

## 最近问题

两个包含明确英文片名的字幕文件：

- `The_Battle_Of_Algiers_1966_BluRay_Criterion_Collection_1080p_AVC.srt`
- `The_Battle_of_Algiers_1966_REMASTERED_CUSTOM_MULTi_VFF_1080p_BluRay.srt`

都被自动导向了错误条目：

`Marxist Poetry: The Making of The Battle of Algiers (2004)`

正确目标应为：

`The Battle of Algiers / La battaglia di Algeri (1966)`

## 直接原因

本次不是文件名解析完全失败。

现有解析器已经能提取：

- title: `The Battle of Algiers`
- year: `1966`
- release markers: `BluRay`, `Criterion Collection`, `REMASTERED`, `VFF` 等

真正问题在自动候选采纳层：

1. TMDB 返回了一个标题中包含 `The Battle of Algiers` 的纪录片候选。
2. 该候选年份为 2004，与文件名年份 1966 不符。
3. 旧逻辑只要 `sortedResults.length > 0`，就会自动选择第一名。
4. 候选排序有加减分，但没有“低于最低置信度禁止自动应用”的硬门槛。

因此，弱候选被错误地升级成了已确认片源。

## 为什么多次迭代仍反复出错

### 1. 查询生成和候选采纳没有被严格分层

过去多次修复主要集中在：

- `parseMediaFilename`
- `cleanFilename`
- `buildTmdbSearchQueries`
- `assessMediaIdentity`

这些解决的是“拿什么去搜”。

但阿尔及尔问题发生在“搜到了以后是否能自动确认”。即使查询词正确，如果采纳策略太宽松，仍然会错。

后续必须把链路拆成三层独立判断：

- 识别层：文件名是否提供可靠片名、年份、季集号。
- 查询层：应该发起哪些有限查询，避免无意义 API 压力。
- 采纳层：返回候选是否足够可靠，是否允许自动应用。

### 2. 回退策略为了命中率不断变宽

为了解决 `Down Cemetery Road XXX`、中文剧集名、无明确英文名等案例，查询逻辑加入了：

- 清洗后的标题回退。
- 片名窗口切片。
- `multi` 与 `movie/tv` 多端点搜索。
- 冒号拆分搜索。
- fallback title。

这些提升了召回率，但也扩大了错误候选进入列表的机会。

召回率提高后，必须同步提高“自动确认门槛”。之前只扩展了搜索，没有同步收紧自动采纳。

### 3. 测试更偏向“能否搜到”，不足以覆盖“是否不该套用”

已有回归覆盖过：

- 脏文件名能回退到正确片名。
- 年份与片名可以用于电影搜索。
- 失败搜索不清空已有 metadata。
- 弱 release 参数不应预填 AC3 等噪声。

但缺少负样本：

- 只返回标题包含但年份不符的候选时，不能自动套用。
- 返回 making-of、纪录片、花絮、短片时，不能自动覆盖正片。
- 候选列表可展示，但 metadata 必须保持空或保留旧值。

没有这些负样本，代码很容易在“提高命中率”的同时引入误命中。

### 4. TMDB 数据本身不是严格片名数据库

TMDB 搜索会返回：

- 正片。
- making-of。
- documentary。
- special。
- collection。
- 同名短片。
- 翻译名或别名包含关键词的项目。

所以不能把“TMDB 返回了结果”视为“找到了片源”。搜索结果只是候选，不等于确认。

### 5. 文件名信息被用来搜索，但没有充分参与候选拒绝

文件名里的 `1966`、`BluRay`、`Criterion Collection`、`REMASTERED` 等信息不一定都用于搜索，但它们应该作为候选校验信号。

当前最重要的是年份：

- 文件名有电影年份时，年份不符应大幅降权。
- 年份不符但标题包含，不应自动应用。
- 年份匹配且片名精确/近似匹配，才可自动应用。

发行商、载体、平台信息后续可作为“版本风险提示”，不一定进入 TMDB 搜索。

## 当前修正

已在 `searchTmdb` 自动搜索链路中加入显式采纳判断：

- `auto_apply`：候选可自动写入 `tmdbData`。
- `require_confirmation`：候选只展示，不自动写入。
- `reject`：候选不允许自动应用，后续可继续收紧展示策略。

当前硬规则：

- 文件名明确提供电影年份时，候选年份不符不得自动应用。
- 电影文件名不得自动应用 TV 候选。
- making-of、behind-the-scenes、documentary、featurette、interview、special、中文纪录片/幕后/花絮/访谈词或纪录片 genre 候选不得自动应用。
- 文件名有年份时，标题只是 contains / loose contains 的候选不得自动应用。
- 分数低于场景门槛时不得自动应用。

弱候选处理方式：

- 保留在候选列表中。
- 打开/提示手动确认。
- 不自动写入 `tmdbData`。
- 不覆盖片源卡片与输出文件名。

新增回归样本：

- Criterion Collection 文件名必须匹配 1966 正片。
- REMASTERED / VFF 文件名必须匹配 1966 正片。
- 只返回 2004 making-of 纪录片时，不得自动应用。
- 只返回同年纪录片/花絮候选时，不得自动应用。
- 只返回同年但标题仅部分包含片名的候选时，不得自动应用。
- 中文片名跨语种搜索只返回纪录片/幕后候选时，不得自动应用。
- 电影文件名只返回 TV 候选时，不得自动应用。

## 后续改动原则

### 原则一：自动应用必须比候选展示更严格

候选可以宽，自动确认必须窄。

允许展示：

- 标题部分包含。
- 别名包含。
- 年份缺失。
- 类型不完全确定。

允许自动应用：

- 类型符合电影/剧集预期。
- 年份匹配或没有年份约束。
- 片名达到精确或高置信近似匹配。
- 分数达到当前场景最低门槛。

### 原则二：任何新增回退都必须配一个负样本

如果增加一种查询回退，例如：

- 切片查询。
- 冒号拆分。
- 字幕正文提取候选。
- 中文片名转英文片名。
- 文件夹名 fallback。

必须同时增加至少一个“不能自动应用”的样本。

### 原则三：不要为了单个案例无限增加 API 查询

优先使用已有查询结果做更好的排序和拒绝。

只有在以下条件同时满足时才考虑新增查询：

- 原文件名身份强。
- 当前候选为空。
- 新查询可以明显减少噪声。
- 有对应回归样本保护 API 调用数量。

### 原则四：弱匹配进入手动确认，不进入 metadata

弱匹配的正确位置是 `tmdbSuggestions`，不是 `tmdbData`。

UI 文案应表达为：

- “候选需要确认”
- “找到相近片源”
- “片名或年份不够吻合”

避免表达成：

- “已匹配”
- “已关联”
- “已找到片源”

## 必备回归矩阵

每次修改 TMDB 链路，至少检查以下类别：

| 类别 | 样本 | 预期 |
| --- | --- | --- |
| 强电影名 + 年份 | `The_Battle_of_Algiers_1966...` | 自动匹配 1966 正片 |
| 标题包含但年份不符 | making-of 2004 | 只进候选，不自动应用 |
| 脏剧集名 | `Down.Cemetery.Road.S01E02...` | 自动匹配剧集 |
| 弱参数名 | `2024.1080p.HEVC.AC3.5.1.ass` | 不自动搜索，不填 AC3 |
| 中文季集名 | `金斯敦市长第四季第五集.srt` | 保留季集信息，提示补片名 |
| 纯季集号 | `S04E05.srt` | 不自动搜索，提示补片名 |
| 搜索失败但已有 metadata | 已有关联后搜索失败 | 不清空已有 metadata |
| 多文件同项目 | 同剧不同集字幕包 | 不对每个文件重复错误覆盖 |

## 结论

反复出错不是因为某一个正则写错，而是因为 TMDB 关联链路同时承担了三个任务：

1. 从混乱文件名中恢复片名。
2. 尽量少请求 API 但提高召回。
3. 自动替用户确认最可能的片源。

前两个任务追求“尽量找到”，第三个任务必须追求“宁可不自动确认，也不能错确认”。

后续所有迭代都要先问：

这次改动是在提高召回，还是提高采纳可靠性？

如果是提高召回，必须同步增加误采纳保护。
